## Secret handling hard rules

Secret material must never be:

- printed in terminal output;
- pasted into ChatGPT;
- written into `APC_LAST_OUTPUT`;
- committed to git;
- stored in Source files;
- included in docs or smoke scripts;
- exposed through public routes;
- embedded directly in a systemd unit file;
- stored in shell history;
- generated by a command that echoes the value.

Secret validation must prove presence, ownership, permissions, and runtime wiring without printing the value.

## Recommended future secret delivery design

A future apply phase should use a root-owned environment file or equivalent secure delivery mechanism.

Recommended CT202 policy:

- secret file path should be outside the repository;
- secret file should be owned by root;
- secret file mode should be `0600`;
- service runtime user should receive the needed value only through systemd environment injection;
- the systemd unit should reference an environment file path, not embed the secret value;
- validation should check file existence, owner, mode, and variable-name presence without printing the variable value;
- rotation should be possible by replacing the file and restarting only in an explicitly approved runtime phase.

No file is created by Phase 14J-GU.

## Public API key policy

For future CT202 controller runtime, the public API key should be treated as secret runtime configuration, even if it is used for public route authorization.

Policy:

- do not commit the key;
- do not place the key in Source files;
- do not place the key in ChatGPT;
- do not write the key to `APC_LAST_OUTPUT`;
- do not print the key during generation or validation;
- do not store the key in the systemd unit body;
- inject it through a secured runtime environment mechanism;
- rotate it during an approved maintenance/cutover phase;
- validate by checking a hash/fingerprint only if the fingerprint itself is intentionally non-secret and safe to record.

## Proposed future file and unit pattern

This is a policy pattern only, not an apply.

Future candidate pattern:

- root-owned CT202 runtime environment file outside repo;
- mode `0600`;
- systemd `EnvironmentFile` reference to that file;
- runtime reads public API key from environment;
- unit still binds to loopback unless a later route/runtime plan changes that;
- no value is printed in creation or validation;
- no secret appears in `systemctl cat` output except safe variable names and file paths.

The exact future path and variable names must be approved before an apply phase.

## Future validation checklist

A future apply phase must validate without printing secret values:

1. environment file exists;
2. owner is root;
3. mode is `0600`;
4. required variable names exist;
5. no value is printed;
6. systemd unit references only the file path;
7. systemd unit does not embed any secret value;
8. `systemctl cat` output is safe to paste after sanitization;
9. runtime loopback auth smoke passes with sanitized output;
10. service returns to disabled/inactive if the phase is a rehearsal/no-enable phase.

## Future rotation checklist

A future rotation phase must define:

- who initiates rotation;
- how a new key is generated without printing;
- how the old key is invalidated;
- whether both old and new keys can overlap briefly;
- whether restart is required;
- rollback if the new key fails;
- sanitized verification;
- no key material in logs, repo, Source, or ChatGPT.

## Rejected designs

Rejected for CT202 persistent runtime:

- putting any secret value directly in a committed file;
- putting any secret value in Source documents;
- putting any secret value in a systemd unit body;
- pasting any secret value into ChatGPT;
- writing any secret value to `APC_LAST_OUTPUT`;
- storing any persistent public API key in shell command history;
- using a broad/global Cloudflare API key for this CT202 controller runtime policy.
